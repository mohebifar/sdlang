# Round 10: editor's independent scores

Written and committed before running Codex's scoring round, without seeing its scores.
Scale and areas as in REVIEW.md. These score the design on paper; nothing is validated
until the first milestone runs.

| Area | v0 | Editor now | Why | What would make it a 9 |
| --- | --- | --- | --- | --- |
| Architecture (graph, identity, state, plan actions) | 7 | **8** | Transactions over compatibility groups, named projections with consumed/observed relations, fixed-point propagation over old and new graphs, plan binding with a journal and amendments, contingent envelopes, applied-vs-desired graph. Every REVIEW flaw in this area has a written fix. Held back by sheer concept count: a reader needs projections, relations, obligations, transactions, envelopes and evidence before the first plan makes sense, and none of the propagation rules has been run on a real change set. | A worked trace of propagation for two or three nontrivial changes (an interface break, a behaviour change, a repair) showing the exact obligations and transactions, so the rules are demonstrated rather than asserted. |
| Drift and brownfield | 6 | **8** | One-owner invariant, slots and created outputs with stable keys, transfer as a member move, contributions with an aggregation contract, toolchain and retained artifacts with owners, exact versus formatted digests, four drift resolutions, and `spec import` as a reviewed ownership mapping. Whole-file ownership only; `absorb` and `import` still lean on an agent to draft spec text, with no stated quality bar. | A defined output for `absorb`/`import` (what the drafted spec patch must contain and how it is checked), and one brownfield walk-through. |
| Verification | 6 | **8.5** | Evidence kinds with explicit promises and non-promises, conjunctive policies, coverage separated from runs, oracle digests, complete discovery, flake handling, oracle amendments, narrow conformance rules. Honest about what review can and cannot establish. Still depends on agent reviewers for coverage, and mutation testing was dropped. | An evaluation hook: how coverage-review quality is measured in the milestone (for example seeded weak tests the reviewer must reject). |
| Grammar and syntax | 5 | **9** | Complete EBNF with lexical rules, string state machine, dedent, newline policy, resolution algorithm, annotations, selectors, value/type matrix. A checker parses every example and rejects sixteen negative cases. The checker does not implement name resolution or schema checking, so "every construct is defined" is verified by reading, not by a tool. | Already at the bar for a design draft. |
| Agent interop | 5 | **8.5** | Four JSON Schemas with generated, validated examples; recomputable bindings; classified retries; blocker taxonomy; deterministic context packing; review protocol; generator protocol. The MCP tools and the generator protocol are prose tables rather than schemas, and the rendered Markdown prompt is unspecified. | Schemas for the MCP tool inputs and outputs and for the generator protocol. |
| Package ecosystem | 4 | **7** | The design now asks for very little: a closed kind vocabulary, no package code during planning, one narrow hard-coded adapter, cheap local kinds, bare capabilities. That is the right response to the risk. But the risk itself (nobody has written packages; the value depends on adapters existing) is not something a document can remove. | A written `nextjs` adapter definition in this syntax (kinds, exports, checks) that the checker parses, showing the vocabulary is sufficient for the one adapter the milestone needs. Even then, the ecosystem risk caps this area until adapters exist. |

Overall: about 8 as a design draft, up from 6. The largest remaining risks are the ones
REVIEW.md named: nothing is validated, and the ecosystem does not exist.
