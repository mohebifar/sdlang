The **new defects and integration gaps**, in priority order:

1. **The supplied build commands cannot satisfy the new check ABI as documented.** The ABI requires one JSON result on stdout and exit 0; every other exit is infrastructure failure. The adapter still directly invokes `tsc --noEmit` and `next build`, with no declared protocol wrapper. Moreover, the input promises a read-only working tree, but the build declaration provides no mechanism for routing build output into scratch. An adapter author must invent the missing runner contract. Either keep exit-status handling for build commands or provide wrapper commands and explicit scratch/output rules. See [ABI](/Users/mohebifar/dev/intentlang/SPEC.md:763), [working-directory contract](/Users/mohebifar/dev/intentlang/schemas/check.schema.json:103), and [adapter commands](/Users/mohebifar/dev/intentlang/examples/nextjs-adapter.int:78).

2. **A conformance check receives the files, but not the contract they must conform to.** The closed input object contains an address, output paths, rules and execution metadata; it contains no declaration kind, canonical fields, applied graph or graph resource handle. The Drizzle example declares `schema_matches_entity`, but cannot obtain the expected entity schema through this ABI. Re-parsing repository specs would require the check to reconstruct the compiler’s applied-graph interpretation itself. Supply the relevant canonical declaration and references, or a defined immutable resource interface. See [input schema](/Users/mohebifar/dev/intentlang/schemas/check.schema.json:24), [partial applied graph](/Users/mohebifar/dev/intentlang/SPEC.md:984), and [Drizzle rule](/Users/mohebifar/dev/intentlang/examples/drizzle-binding.int:71).

   The new inventory also exposes an applicability gap: the same conformance check is attached to actions and pages, but declares `page_default_export` for every invocation. There is no applicability declaration or `not_applicable` result. Explain which rules apply to actions rather than requiring authors to invent vacuous “satisfied” results. See [action checks](/Users/mohebifar/dev/intentlang/examples/nextjs-adapter.int:56), [inventory](/Users/mohebifar/dev/intentlang/examples/nextjs-adapter.int:97), and [result statuses](/Users/mohebifar/dev/intentlang/schemas/check.schema.json:195).

3. **The checker does not establish the inventory claim in R2.7.** It compares result rules with the input fixture’s `rules`, after filtering out every other subject. It never compares that inventory with the adapter definition. I confirmed that the full schema/example check still passes when an extra result for `unrequested.page` is appended, or when both fixtures replace the adapter’s rules with `invented_rule`. It detects missing or duplicated rules for the expected subject, which is useful, but not exact agreement with the declared check. Compare exact `(subject, rule)` pairs against the adapter-derived inventory and reject extras. See [R2.7 claim](/Users/mohebifar/dev/intentlang/DECISIONS.md:269) and [implementation](/Users/mohebifar/dev/intentlang/tools/check_examples.py:670).

   The test example has no paired test-input cross-check. Replacing its cases with an empty list and changing its snapshot still passes the checker. Its inventory and input digests are only shape-validated. The new test schema also has no fields for the generator/input/seed metadata required for generated cases. Add paired fixtures and explicit binding/inventory rules; retain the generated-case metadata or narrow that promise. See [example registration](/Users/mohebifar/dev/intentlang/tools/check_examples.py:507), [test result schema](/Users/mohebifar/dev/intentlang/schemas/check.schema.json:219), and [test identity promise](/Users/mohebifar/dev/intentlang/SPEC.md:1425).

4. **Plan-cadence publication is only partially specified.** The exception at [SPEC:914](/Users/mohebifar/dev/intentlang/SPEC.md:914) explicitly permits publication before these checks pass, so the basic transaction rule is not simply an overlooked contradiction. But older operative text still says the CLI runs every check before review, and verification says build is an obligation of every transaction. The new section never specifies the publication step that attaches the final build receipt to already-committed state records. See [dispatch lifecycle](/Users/mohebifar/dev/intentlang/PROTOCOL.md:65), [transaction obligations](/Users/mohebifar/dev/intentlang/SPEC.md:1333), [state evidence](/Users/mohebifar/dev/intentlang/SPEC.md:857), and [plan cadence](/Users/mohebifar/dev/intentlang/SPEC.md:1086).

   Its status rule also says `unverified` until the build passes, whereas the general precedence requires `failed` for failed evidence and `stale` for stale evidence. The CI findings table describes unmet **requirement** policies but does not explicitly cover an outstanding mandatory build on a declaration without requirements. Define pending, failed and stale plan checks, their persisted receipts, and their CI finding. See [status precedence](/Users/mohebifar/dev/intentlang/SPEC.md:1377) and [CI findings](/Users/mohebifar/dev/intentlang/SPEC.md:1133).

   Finally, bisection cannot guarantee the promised *first* failing transaction without monotonicity: intermediate deferred builds may fail, recover, then fail again. Weaken that attribution claim or specify an algorithm that handles nonmonotonic results. See [failure recovery](/Users/mohebifar/dev/intentlang/SPEC.md:1089).

5. **The applied store lacks a complete retention/currency contract.** Its stated roots are state `hashes` and `consumed` entries. Yet the reference context projection contains hashes of inherited text rather than that text itself, and module headers have no state records. The text does not specify transitive retention of those referenced values, even though protocol orders require previous inherited text. Saving the outer projection alone does not recover that text after history disappears. Define transitive content retention, including `context_parts`, rather than promising that squash/rebase loses nothing. See [store rules](/Users/mohebifar/dev/intentlang/SPEC.md:878), [context declarations](/Users/mohebifar/dev/intentlang/SPEC.md:79), [context hashing](/Users/mohebifar/dev/intentlang/tools/canon.py:162), and [previous-text requirement](/Users/mohebifar/dev/intentlang/PROTOCOL.md:111).

   The store is also absent from the explicit checked-input exclusions. Adding or collecting `.spec/applied/` files can therefore change a project check’s whole-tree closure. Specify whether these files are excluded metadata and when store updates occur relative to checks; otherwise bookkeeping can stale evidence. See [publication exclusions](/Users/mohebifar/dev/intentlang/SPEC.md:1083) and [whole-tree currency](/Users/mohebifar/dev/intentlang/SPEC.md:1393).

6. **“Merge by any method” exceeds the reconciliation mechanism.** On conflict, the driver retains the current file and records its name. Later reconciliation reads the base and both parents from Git. A squash or rebase result does not necessarily retain those two original parents, and the marker is not specified to retain their identities or contents. The content store preserves values, not merge ancestry. Persist the conflict’s three inputs when the driver has them, or narrow the supported workflow. See [merge-method promise](/Users/mohebifar/dev/intentlang/SPEC.md:1154), [driver](/Users/mohebifar/dev/intentlang/SPEC.md:1158), and [binding requiring at least two parents](/Users/mohebifar/dev/intentlang/schemas/plan.schema.json:70).

7. **The new `lib` adapter cannot independently fulfil its tested example.** The example has an `expect`; `implements lib` supplies only `main`, no test slot or creation root, while test checks run once per test output. A create dispatch has no specified place to write the required test. Define a test output or an explicit cross-owner test workflow. See [`lib` example](/Users/mohebifar/dev/intentlang/SPEC.md:568), [adapter](/Users/mohebifar/dev/intentlang/examples/nextjs-adapter.int:60), [test invocation](/Users/mohebifar/dev/intentlang/SPEC.md:745), and [write envelope](/Users/mohebifar/dev/intentlang/SPEC.md:1057).

   Its contract also needs an explicit limit: export names do not express signatures or distinguish type/value exports, and `uses` observes no behaviour. A helper’s normative behaviour change therefore does not trigger the caller review that an action’s change would. This follows the relations table, but conflicts with the unqualified statement that behaviour changes get review “whatever their types say.” Clarify that limit and integrate `lib` into Compatibility and export-mode rules. See [`lib` contract](/Users/mohebifar/dev/intentlang/SPEC.md:578), [relations](/Users/mohebifar/dev/intentlang/SPEC.md:167), [export metadata](/Users/mohebifar/dev/intentlang/SPEC.md:677), and [Compatibility](/Users/mohebifar/dev/intentlang/SPEC.md:710).

8. **Two cost-control promises have no wire representation.** Reconfirmation requires an `unchanged` answer, but coverage verdicts only allow `sufficient`, `insufficient`, or `cannot_determine`; no reconfirmation assessment carries the old/new oracle relationship. Separately, `--accept-cost` must record acceptance in the immutable plan, whose closed schema has no acceptance field. Both are prose-only additions until their representation and transitions are defined. See [reconfirmation](/Users/mohebifar/dev/intentlang/SPEC.md:1431), [verdict enum](/Users/mohebifar/dev/intentlang/schemas/review-verdict.schema.json:38), [cost acceptance](/Users/mohebifar/dev/intentlang/SPEC.md:1108), and [plan schema](/Users/mohebifar/dev/intentlang/schemas/plan.schema.json:6).

9. **The scope split and several references remain inconsistent.** The first milestone explicitly requires builds once per plan, then explicitly defers plan-cadence checks. It also says the adapter has one conformance rule when the adapter declares two. These are direct contradictions. See [milestone](/Users/mohebifar/dev/intentlang/SPEC.md:1732), [deferral](/Users/mohebifar/dev/intentlang/SPEC.md:1763), and [adapter inventory](/Users/mohebifar/dev/intentlang/examples/nextjs-adapter.int:100).

   More broadly, `entity`, `rule` and `environment` remain listed as core while entity classification, rules and environments are provisional; the core plan schema still requires a rollout object. Keeping the extended worked example is explicitly intentional, but it does not provide a small, self-contained core example. Mark the profiles consistently and supply a core-only fixture. See [core kinds](/Users/mohebifar/dev/intentlang/SPEC.md:445), [extension boundary](/Users/mohebifar/dev/intentlang/EXTENSIONS.md:3), and [required rollout](/Users/mohebifar/dev/intentlang/schemas/plan.schema.json:8).

   Smaller editorial residue: the test protocol is referenced as “below” although it is above, and `DECISIONS.md` still says findings 1–7 “are not applied.” The `Runtime state` links do still reach a forwarding section; I would not call those dead references. See [test reference](/Users/mohebifar/dev/intentlang/SPEC.md:1448), [stale status](/Users/mohebifar/dev/intentlang/DECISIONS.md:260), and [forwarding section](/Users/mohebifar/dev/intentlang/SPEC.md:1475).
